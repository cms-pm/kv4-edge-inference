LegacyRAG: A VRAM-Aware Retrieval-Augmented
Generation
Pipeline for Legacy Multi-GPU Inference via Vulkan
Azeez Shaik
Ying Wu College of Computing
New Jersey Institute of Technology
Newark, NJ, USA
as4768@njit.edu
Abstract—Retrieval-Augmented Generation (RAG) pipelines are
increasingly deployed for privacy-sensitive document intelligence
in resource-constrained organizations. Existing RAG systems
assume modern GPU hardware with FP16 acceleration, large
VRAM, and stable inference throughput. This paper presents
LegacyRAG, a VRAM-aware RAG pipeline for end-of-life GPU
hardware abandoned by CUDA but still viable through the Vulkan
compute API. We deploy LegacyRAG on a dual NVIDIA Quadro
K4200 workstation (Maxwell architecture, 4 GB VRAM per card,
compute capability 3.0, dropped from CUDA 11.0 [2]) running a
3.82 B parameter quantized language model [5] via the llama.cpp
Vulkan backend [3]. A pre-operation VRAM scheduler queries
both GPUs via nvidia-smi before every embedding operation
and routes workloads to CPU or GPU based on live free-VRAM
thresholds, preventing out-of-memory crashes under concurrent
load. Empirical evaluation reveals that generation dominates
RAG pipeline latency at 99.86%, sustained generation throughput
ranges from 0.29 to 1.66 tok/s due to non-deterministic Vulkan
behavior on legacy hardware, and naive dual-GPU layer splitting
degrades prompt prefill by 50 × (from ∼26 to 0.52 tok/s) while
leaving decode speed unchanged. The VRAM scheduler logged
fifteen decisions with zero OOM events. LegacyRAG is released
as open-source software to support reproducible research on
constrained-hardware AI inference.
Index Terms—edge computing, retrieval-augmented generation,
legacy GPU inference, Vulkan compute, VRAM scheduling, onpremise AI, resource-constrained systems
I. INTRODUCTION
The commoditization of large language models (LLMs) has
created strong demand for on-premise AI inference in privacysensitive domains such as municipal government, healthcare,
and legal services. Organizations in these sectors cannot route
document queries through cloud APIs due to data sovereignty
requirements, yet rarely have the budget for modern GPU
hardware [7]. This creates a deployment gap: institutions with
genuine AI needs and existing legacy workstation infrastructure
have no well-characterized path to local LLM deployment.
This gap is compounded by a sharp ecosystem cliff in GPU
software support. NVIDIA dropped compute capability 3.0
(Kepler) from CUDA 11.0 in 2020 and removed all remaining
Kepler support in CUDA 12.0 [2]. Cards such as the Quadro
K4200 and GeForce GTX 750 Ti—common in institutional
workstations from 2013–2016—are invisible to every modern
LLM inference framework that depends on CUDA. The Mesa
NVK project provides Vulkan 1.2 conformance for these
cards [12], offering a GPU compute path without CUDA.
RAG [1] further complicates deployment on legacy hardware
because it requires two concurrent GPU workloads: an embedding model for document retrieval and a generation model for
answer synthesis. On constrained hardware these workloads
compete for VRAM, and naive co-scheduling causes out-ofmemory (OOM) crashes. Multi-GPU inference literature [9]
shows that inter-device synchronization dominates throughput
at low memory bandwidth, a finding our experiments confirm
on Maxwell-class hardware.
This paper makes four contributions:
1) We demonstrate that Vulkan [4] provides a viable path to
GPU-accelerated LLM inference on CUDA-abandoned
hardware, achieving a 1.39 × generation speedup over
CPU-only inference on the Quadro K4200.
2) We design and implement LegacyRAG, a VRAM-aware
RAG pipeline with a pre-operation scheduler that queries
live GPU memory state and routes embedding workloads
to prevent OOM conditions.
3) We empirically characterize RAG pipeline performance
on dual Maxwell GPUs via Vulkan, reporting generation
throughput variance, full latency breakdown, and multiGPU split behavior under PCIe-only interconnect [9].
4) We show that dual-GPU Vulkan layer splitting is counterproductive on Maxwell hardware without NVLink,
degrading prefill 50× due to inter-device synchronization
overhead.
LegacyRAG is publicly available at https://github.com/
azeez-1904/LegacyRAG.
II. BACKGROUND ANDRELATEDWORK
A. Retrieval-Augmented Generation
Lewiset al.[1] introduced RAG as a framework augmenting
generative models with a retrieval component. A standard RAG
pipeline consists of: (1) document ingestion with chunking and
embedding, (2) vector similarity retrieval, and (3) contextconditioned generation. Embedding models (100–500 MB)

benefit from batched GPU execution, while generation models
(2–70 GB) require sustained VRAM throughout inference. On
VRAM-limited hardware these requirements create a scheduling
conflict that LegacyRAG addresses.
B. LLM Quantization for Constrained Hardware
Frantaret al.[10] introduced GPTQ, an accurate one-shot
post-training quantization method enabling 7B+ models in
under 4 GB VRAM. Linet al.extended this with AWQ [11],
the MLSys 2024 Best Paper, demonstrating 4-bit deployment on
edge devices with minimal accuracy degradation. LegacyRAG
uses GGUF Q4 0 quantization in llama.cpp [3], reducing phi3mini [5] from∼7 GB FP16 to 2.03 GiB.
C. Edge and On-Premise LLM Inference
Zhouet al.[7] characterize the “last mile” of AI deployment, showing edge inference is essential for latency-sensitive
and privacy-sensitive workloads. Recent work on on-device
inference [8] demonstrates speculative decoding for mobile
hardware, but assumes compute capability ≥6.0 (Pascal) and
does not address CUDA-abandoned Maxwell cards. To our
knowledge, no prior published work has characterized full RAG
pipeline performance on Maxwell-era hardware via Vulkan.
D. Multi-GPU Parallelism and Communication Overhead
Narayananet al.[9] showed that sub-optimal tensor and
pipeline parallelism combinations reduce throughput by up to
2× even with high-bandwidth NVLink. On PCIe-only hardware
as in our dual K4200 setup this effect is far more severe, as
our prefill degradation experiments confirm (Section IV-F).
III. SYSTEMDESIGN
A. Hardware Configuration
Table I summarizes the test platform. Each Quadro K4200
(Maxwell GM204, 2014) provides 1,344 CUDA cores and
4 GB GDDR5 at 173 GB/s. At Vulkan initialization, both
cards report fp16: 0 , int dot: 0 , and matrix cores:
none. The host CPU is an Intel Xeon E5-1620 v3 (Haswell, 4
cores / 8 threads, 3.50 GHz base, 3.60 GHz max turbo, 10 MB
L3 cache). Both K4200s occupy PCIe 3.0 x16 slots on the
Dell Precision Tower 5810 motherboard.
B. Architecture Overview
LegacyRAG is a FastAPI service exposing POST /ingest
and POST /query endpoints. Ingest chunks input documents
into 512-character overlapping windows (64-character stride),
embeds each chunk via the VRAM-aware scheduler, and stores
normalized 768-dimensional vectors to a persistent NumPy
store. Query embeds the question using nomic-embed-text [6],
retrieves top-k chunks by cosine similarity, and generates an
answer via the local llama.cpp server [3]. Fig. 1 shows the
pipeline.

C. VRAM Scheduler
The VRAM scheduler is the core contribution of LegacyRAG.
Before every embedding operation it runs:
nvidia-smi --query-gpu=index,memory.free
--format=csv,noheader
and routes by the following policy:
1) If any GPU reports free VRAM below Tvram (default:
800 MB), route to CPU.
2) If a GenerationContext lock is active (generation
in progress), route to CPU regardless of VRAM state.
3) Otherwise, route to GPU.
Every decision is timestamped and appended
to schedule_decisions.jsonl. The
GenerationContext is a thread-safe counter that
prevents the embedding model [6] ( ≈280 MB peak) from
competing with active generation for VRAM. The threshold
Tvram = 800 MB was selected empirically. With phi3-mini
occupying ≈2.1 GB and the KV cache allocating up to 1.5 GB,
GPU 0 maintains 1,400–1,550 MB free and GPU 1 maintains
≈1,994 MB free under normal load, providing ≈600 MB
margin above the embedding model’s peak.

IV. EVALUATION
A. Experimental Setup
Experiments ran on a Dell Precision Tower 5810 (Ubuntu
24.04) with an Intel Xeon E5-1620 v3 (4 cores, 8 threads,
3.50 GHz) and dual K4200s in PCIe 3.0 x16 slots. The
llama.cpp server [3] (b5576) used the official Vulkan binary.
The test corpus was a five-chunk public records policy document (≈2,500 tokens). All queries used a 459-token prompt
with 512 maximum completion tokens.
B. CPU-Only vs. Single-GPU Vulkan
GPU Vulkan achieves a 1.39 × generation speedup (9.07
vs. 6.52 tok/s). Prompt evaluation is slower on GPU (8.85 vs.
21.14 tok/s) because the K4200’s lack of FP16 and integer
dot-product instructions forces FP32 fallback in the Vulkan
backend [4]. Autoregressive decode benefits from GPU memory
bandwidth (173 GB/s vs. ≈45 GB/s dual-channel DDR4 on the
E5-1620 v3), explaining the generation speedup.
C. RAG Pipeline Benchmark

sequential requests following the architecture of Lewiset al.[1].
Generation accounts for 99.86% of total pipeline latency;
embedding 0.14%; retrieval <0.001%. Any acceleration of
embedding or retrieval—including the quantization gains of

D. Generation Throughput Variance
Three identical sequential requests produced 0.89, 1.66,
and 0.29 tok/s—a 5.7 × range (Fig. 3). Three mechanisms
contribute:
Thermal throttling.Maxwell does not expose GPU frequency monitoring through Vulkan [4], making throttle events
silent. Request 3 (0.29 tok/s, 525 s for 150 tokens) exhibited
substantially lower throughput under nominally identical conditions, consistent with thermal onset.
Queue-induced warm-up.Request 2 (1.66 tok/s) followed
Request 1 immediately, benefiting from residual warm VRAM
caches and pre-compiled Vulkan shader pipelines. Cold-start
requests (1 and 3) were slower.
KV cache pressure.The KV cache grows within the fixed
4 GB VRAM budget, increasing memory pressure late in long
generation runs.
E. VRAM Scheduler Behavior
All fifteen scheduling decisions routed embeddings to GPU
(Table IV, Figs. 4–5). Both cards maintained free VRAM well
above the 800 MB threshold throughout. Zero OOM events
occurred. The CPU fallback provides a safety margin for
deployments where display servers, browsers, or secondary
applications share GPU 0 memory—a common scenario in
institutional workstations that would otherwise produce silent
OOM failures.

analysis of Narayananet al.[9]: during prefill, all prompt

layer crossing the inter-GPU boundary requires a Vulkan
pipeline barrier, multiplied by the full prompt length. During
decode, a single token is generated per step and the per-step
synchronization cost is amortized. Unlike NVLink-connected
clusters [9], the PCIe 3.0 bus between the two K4200s has
insufficient bandwidth to amortize multi-layer barrier overhead
at prefill scale.
Three simultaneous requests all failed with first-token
timeouts (600 s each, batch wall time 1,800 s). With llama.cpp
serializing requests through a single inference slot [3] and each
generation taking 308–575 s, concurrent operation is infeasible
on this hardware. Single-GPU inference with CPU embedding
offload via the VRAM scheduler is the optimal configuration.
V. DISCUSSION
A. Practical Deployment Envelope
Single-user sequential workloads with 308–575 s end-to-end
latency are feasible for asynchronous use cases such as batch
document processing and low-frequency queries in institutional
settings [7]. The total hardware cost for this deployment is
approximately $200–$300 for a used Dell Precision Tower
5810 with dual K4200s on the secondary market, with zero
per-query API cost and no data egress for sensitive documents.

B. Value of VRAM-Aware Scheduling
The CPU fallback path was not triggered in our experiments
because VRAM stayed above threshold throughout. Its value is
preventive: in institutional deployments where display servers
and browser processes share GPU 0, available VRAM can
drop by several hundred megabytes, bringing it toward the
800 MB threshold. Without the GenerationContext guard,
a concurrent embedding request during active generation could
consume the ≈280 MB needed by nomic-embed-text [6] and
cause a mid-generation OOM crash.
C. Vulkan as a Long-Term Path
The NVIDIA 470 driver providing Vulkan 1.2 on the
K4200 was declared end-of-life in September 2024. The Mesa
NVK driver [12] provides an actively maintained open-source
alternative with Vulkan 1.2 conformance for Kepler and later
GPUs. LegacyRAG is driver-agnostic and functions with NVK,
extending the viable service life of this hardware class.
D. Limitations
Three requests with a single prompt type are insufficient for
robust statistical characterization of throughput variance; future
work should use ≥50 requests with varied prompt lengths. The
test corpus (five chunks, ≈2,500 tokens) does not evaluate
retrieval at scale. The CPU fallback path’s latency impact
was not measured because the threshold was never breached.
Results are specific to the K4200; cards with different VRAM
(e.g., K5200 with 8 GB) may differ materially.

VI. CONCLUSION
LegacyRAG demonstrates that practical LLM document
intelligence is achievable on CUDA-abandoned Maxwell
hardware via Vulkan [4]. By pairing the llama.cpp Vulkan
backend [3] with a pre-operation VRAM scheduler and a
GenerationContext guard, the system achieves GPUaccelerated RAG [1] on dual Quadro K4200s with zero OOM
events.
Key findings: Vulkan delivers a 1.39 × generation speedup
over the E5-1620 v3 CPU baseline; generation dominates RAG
latency at 99.86%, making embedding and retrieval optimization largely irrelevant for this hardware class; throughput is
non-deterministic (0.29–1.66 tok/s) under sustained load due to
silent thermal throttling; dual-GPU layer splitting degrades prefill by 50 × due to PCIe-bound Vulkan barrier overhead [9]. A
usable private RAG deployment is achievable for ≈$200–$300
in used hardware. Full code, benchmark data, and scheduler
logs are at https://github.com/azeez-1904/LegacyRAG.
